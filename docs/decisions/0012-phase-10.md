## 3. Finding P10-FA — third-party client network loads

> Provenance: P10-R0 authorization appendix. Verbatim-as-supplied: YES.
> Status: ratified.
> Marking (P10-R1): verbatim under the P10-N1 state-1 definition — the
> single `\<link\>` escape is Markdown-only escaping of the source's
> literal `<link>`.

Basis.

Remote asset loading from a client that renders private correspondence is
a disclosure channel, not UI residue.

A remote image URL causes the reader's browser to contact a third-party
host. That host learns the reader's IP address and the moment of reading.
Where the URL is supplied by a sender, the sender learns when a specific
recipient opened a specific letter — recipient telemetry obtained without
any act by the recipient and without their knowledge.

This is a bounded-disclosure violation delivered through styling. It
survived the Phase 0.5 constitutional strip because it did not look like
a mechanic.

Ruling.

No third-party network load of any kind is permitted from the client in
this slice.

Specifically prohibited:

- remote font loading, including Google Fonts @import and \<link\>;
- remote stylesheet or script loading from any origin;
- remote image rendering, including seed/sample imagery;
- any surface accepting a user-supplied remote URL for rendering;
- any replacement network dependency introduced to restore visual
  fidelity.

All fonts and assets are local.

`photo` remains declared and unimplemented under 0007. This finding does
not implement it, reserve for it, or authorize a local-upload substitute.

Prospective rule.

Any future remote fetch originating from a surface that renders private
correspondence returns to chamber before implementation. This holds
regardless of the load's apparent innocuousness — analytics, fonts,
avatars, embeds, previews, and error reporting are all within scope.

Enforcement split across 10.A.

P10-A3 enforces the manifest, lockfile, and CSS/font portion.

P10-A4 enforces the remainder, because the surviving vectors (the seed
image URL, the user-supplied image URL path) are owned by files
physically deleted in that commit.

Per P10-C1 and P10-D1, P10-A3 does not reach into P10-A4-owned files to
satisfy this finding. The complete B4 sweep proving P10-FA is an exit
condition of P10-A4.

## 39. P10-N3 multi-Self provisioning disposition (P10-R13)

> Provenance: P10-N3 ruling and the P10-R13 record authorization, recorded

> Status: ratified. Per P10-P5 this record precedes implementation: P10-S5

### Substrate facts (accepted)

`public.selves` already structurally supports slots 1–3. Three-Self
cardinality is enforced by

    selves_slot_range     CHECK (self_slot BETWEEN 1 AND 3)

together with

    selves_one_per_slot   UNIQUE (account_id, self_slot)

and no application-code cardinality rule substitutes for those constraints.
Enrollment (`auth.enroll_account`) creates slot 1 only. Slots 2 and 3
require no schema change. No client path, no production HTTP route, no
ratified public mutation, no operator command, and no production-side
additional-Self function exists. `GET /auth/selves` already returns every
authoritative Self belonging to the authenticated account. Active Self is
not persisted (0004 R2; R3 places the per-tab selection client-side), so
provisioning creates no active-Self initialization side effect. No handle
registry exists; Self names are non-unique free text subject only to
`selves_name_present`.

### Candidates

**Candidate A — selected:** a reviewed, privilege-scoped operator-side
provisioning mechanism.

**Candidate B — rejected:** the common invariants are already authoritative
schema constraints inherited by both enrollment and later-Self
provisioning; refactoring accepted Phase-4 enrollment code would enlarge the
change surface to remove duplication that does not exist.

**Candidate C — rejected:** fixture-only provisioning lets tests manufacture
multi-Self state but leaves a genuine running development account unable to
reach it.

**Candidate D — rejected:** no committed law authorizes a multi-Self
interface whose only reachable production-shaped state contains one Self.

**Candidate E — factual capacity, rejected as the durable interface:** a
sufficiently privileged operator can insert slot 2 or 3 directly today,
which proves representational capacity; authoritative operational writes
must not depend on undocumented ad-hoc psql where a reviewed,
privilege-scoped, testable boundary is required for later Phase-10 proofs.

P10-S5 is a prerequisite implementation sub-step and lands before Segment
10.C opens. This is not only for switcher demonstration: Segment 10.E must

### Slot policy

Slot is explicit: the operator supplies `--slot`; the intended later-Self
coordinates are 2 and 3. There is no lowest-free selection and no slot
discovery on the operator's behalf — slot is a stable identity coordinate
under `UNIQUE (account_id, self_slot)`, so the operator names the coordinate
being provisioned. The CLI may require the flag and parse its textual value
as an integer, but does not own range validity: no TypeScript rule
substitutes for `selves_slot_range`. No explicit slot-1 prohibition is added
to `auth.add_self`; every account created through the authorized enrollment
path already holds slot 1, so such a call meets the same occupied-coordinate
condition as any other. No separate `count(*) >= 3` cardinality rule is
added.

### Failure contract

    nonexistent account  → PT404
    occupied slot        → PT409

The function must not create an account implicitly, and must not overwrite,
replace, rename, or otherwise mutate the Self occupying a slot. An
out-of-range slot fails through `selves_slot_range`; a blank name fails
through `selves_name_present`; neither schema rule is duplicated in
TypeScript. The P10-S5 completion report records the externally observable
database behavior of those constraint-level failures as fact rather than
inventing application-level contracts for them.

### Privilege invariant

P10-S5 must not widen the application role. The write gate compares the
relevant `selves_app` privilege state before and after the migration and
proves it unchanged: no INSERT on `public.selves`, no EXECUTE on
`auth.add_self`, no new table privilege, no new authoritative write path.
Only `selves_bootstrap` receives EXECUTE on the provisioning function.

### Enrollment unchanged

`auth.enroll_account` remains unchanged and continues to create
`self_slot = 1` directly. P10-S5 sits beside enrollment; it does not
refactor, wrap, or reroute it.

### Name-uniqueness finding

not change this and adds no name uniqueness, handle uniqueness, handle
field, registry, or collision rule. Whether duplicate display names require
switcher disambiguation is a Segment 10.C design question, not a
provisioning question.

authoritative backend state.
